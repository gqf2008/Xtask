## 0. 一句话

**能力是类型化 trait；执行模型写进契约；原子性只由关中断、自旋锁、硬件原子指令提供；
设备操作的长时互斥由单 owner actor 的所有权保证，驱动内部零锁；业务结果与传输错误分开。**

## 2. 真实设备面（v3 的存在理由）

本节是**覆盖面证据**：设备形态取自真实产品类（POS 终端）的设备层——17 个 `*Ops` trait ×
四个后端。它证明 v3 的轴能覆盖真实设备，**不作为契约来源**；规范只依赖这些形态本身，
不依赖某个项目的现状。

| 设备 | 契约要点 | 执行模型 | 生命周期 |
|---|---|---|---|
| Display | `info/clear/draw_text/draw_image/set_backlight(level,timeout)/flush` | Sync | 常驻，双屏 |
| RFCard 非接 | `poll_select/activate/deactivate/wait_remove` + `apdu` + Mifare + `ioctl_raw` | Sync（含阻塞点） | 卡会话 |
| ICCard 接触 | `power_up->ATR / power_down / apdu` | Sync | 卡会话 |
| Pinpad | `KeyStore`（load_key/get_kcv/calc/MAC）+ `PinEntry`（start/events/poll/cancel） | Sync + EventStream | 会话 |
| Scan | `open/start/poll_result->Poll/stop/ioctl_raw` | PollingAsync | open/close |
| WiFi | `scan/connect/status/disconnect/events->Receiver` | EventStream + 同步阻塞 | 单例 |
| BLE | `open/set_adv/connect/GATT/events`（9 类事件） | EventStream | 单例 + 多连接 |
| Keyboard | `get_key_ms(timeout)/clear/is_keypress/events/ioctl_raw` | Sync + EventStream | open/close |
| Printer | `feed/line/dotmatrix/monobmp/barcode/ioctl_raw` | Sync | open/close |
| MagCard | `get_track_data/ioctl_raw` | Sync | open/close |
| DLED | `display/clear_line/light_set/light_get/display_seg/ioctl_raw` | Sync | open/close |
| Audio | `beep_key/beep_play/play/play_tts/stop` | Sync | open/close |
| Keyloader | RKI 四阶段，参数含裸指针 | Sync | 流程 |
| Syncard | SLE4428/4442/AT24CXX/AT1604/1608，裸指针 | Sync | 流程 |
| Board | `init/tick/power_status` | Sync | 常驻 |

片内：GPIO / I2C / SPI / PWM / ADC / UART(tty) / 文件系统（厂商 FS，无块设备层）。

以上设备面来自样本项目（`../sqb_project/src/device/`，非规范）。它把 v2 的运行时前提证伪的六件事：

1. **生命周期**：Printer / Dled / MagCard / Keyboard / Audio / Scanner / BLE 都有
   `open(...)->Dev` + `close(d)`，open 可失败。`&'static` 常驻模型装不下。
2. **三型执行模型**：Sync / PollingAsync / EventStream 并存。v2 只有「非阻塞流 + 唤醒」。
3. **长阻塞 + 超时 + 取消**：`apdu`（~100ms）、`poll_select`、`wait_remove`、`wifi::connect`
   （秒级）、`PinEntry::cancel`。v2 没有超时与取消。
4. **动态子句柄**：`ConnHandle`、`PinSession`、`ScanOp`、`CardId`、`Screen 0/1`。
5. **共享总线必须单 owner**：真实系统把 PM/I2C、WLM/UART、IVR/I2S、Pinpad 全部交给一条
   工作线程串行化（`sqb_bus`）。`BusDevice::transfer(&self)` 的「任意任务可同步调用」不成立。
6. **错误分段 + 业务结果**：厂商错误按模块分段（-300…-4000+）并保留原始负码；扫码/PIN
   的「超时/取消/无卡」是**业务结果**，不是错误。v2 的八变体 `DeviceError` 装不下。
7. **逃生舱是 `ioctl_raw(cmd: u32, argv: *mut c_void)`**，真实面出现 6 次；不存在值类型的
   `Cmd`/`Reply` 渠道。

## 3. 设计原则

0. **规范面向通用嵌入式，项目适配规范**。样本项目只用来证明覆盖面或暴露缺口，
   不能反过来决定契约的形状；需要改的是实现，不是这里的条款。
1. **能力 = 类型化 trait，固定类型，保持对象安全**。每个能力自带具体的 `Outcome`/`Event`/
   句柄类型；关联类型只出现在不用于 `dyn` 的分类骨架上。
2. **执行模型写进契约**：每个能力必须属于 Sync / PollingAsync / EventStream 之一，
   并在方法上标注上下文等级（§4.3）。
3. **生命周期显式**：常驻设备 + `open/close` 状态；独占外设可配 `Drop` 凭证。
4. **原子性与串行化分开**：原子性只用关中断/自旋/原子指令；操作的互斥靠所有权（actor）。
   **驱动内部不加任何锁**。
5. **结果与错误分离**：`Result<Outcome, DeviceError>`；`DeviceError` 保留厂商分段码。

## 4. 并发模型（定稿）

### 4.1 原子性只有三个来源

| 手段 | 保证什么 | 适用 | 失效条件 |
|---|---|---|---|
| **关中断**（`sync::free`） | 同核上任务/ISR 不穿插 | 寄存器序列、与 ISR 共享的状态、注册表/表槽 | 跨核（要自旋）；超过微秒（破坏实时性）；区内阻塞 |
| **自旋锁** | 跨核互斥 | 跨核共享的短临界区 | 同核 ISR 竞争时不带关中断会**自旋等自己**；不能睡眠 |
| **硬件原子指令** | 单字 RMW | 无锁队列、引用计数、标志位 | 多步不变量、跨字段一致性 |

**Mutex 不在这张表里。** 它提供任务级可阻塞互斥，给不了中断意义上的原子性，ISR 里
也不能用。凡是需要「不可被打断」的地方，只有上表三条路。

### 4.2 Mutex 的位置

`sync::Mutex`（带优先级继承的任务阻塞锁）属于**操作系统层可阻塞资源**（Xtask 内核 `src/` 无 `sync::Mutex` 使用者；OS/示例层用它串行化 fs/net 等静态资源）。它**不进驱动**：设备操作的互斥由 actor 的所有权保证（§4.4），
不需要、也不应该在驱动内部出现 Mutex。

理由：驱动方法可能在 ISR 侧被调用（`available`/`register_waiter`/`wake`），Mutex 在那里
不可用；而长操作如果在驱动内取 Mutex，等于把「谁先到谁等」的调度问题塞进了设备契约。

### 4.3 上下文三级

每个方法必须声明自己属于哪一级；**默认 C2**，只有文档明示才能按更低级调用。

| 级 | 名称 | 允许 | 禁止 |
|---|---|---|---|
| **C0** | ISR 安全 | 原子操作、无锁读、`post_isr` | 阻塞、分配、取锁、调用厂商 API |
| **C1** | 任务·短 | 单段 `sync::free` 包住寄存器序列 | 跨毫秒、睡眠、厂商调用 |
| **C2** | 任务·长 | 睡眠、等信号量、厂商 IOCTL（经 actor） | 在 C0/C1 内调用 |

调用方规则：**在 `sync::free` 内只能调用标注为 C0 的方法**。

### 4.4 驱动内部零锁，串行化靠所有权

- 驱动实现只有两件事：C1 的寄存器/状态更新（`sync::free`）+ C0 的原子/无锁接口。
- 「同一设备同一时刻只有一个任务在操作」由**单 owner actor** 保证：一条 owner 任务 +
  命令通道，所有 C2 方法把命令投给 owner，执行完回包。所有权即互斥，驱动代码里
  没有 Mutex、没有锁字段。
- 共享物理总线（I2C/PM、UART/WLM、IVR/I2S、安全芯片）一律经总线 actor；**禁止**任何
  任务直接调厂商 IOCTL。
- 事件通道的发布侧：厂商回调线程用 C1/C2 投递；硬件 ISR 用 C0 的 `post_isr`（定长环，
  无分配）。

### 4.5 `sync::free` 的确切语义

- 形态：**关本核中断 → 抢全局自旋 → 进区 → 放自旋 → 恢复中断**；**可重入**（目标端每核深度
  计数；host 端深度按线程隔离，`nested_free_does_not_deadlock` 测试覆盖）。
  单核下等价于关中断；SMP 下自旋挡别的核。
- **不可重入的是 `Porting::free`（host 上是 `std::sync::Mutex`）与区内取的其他锁**——所以
  区内仍禁止获取任何其他锁（R1 的下半句才是真约束）。
- 因此有一条硬约束：**凡可能在 `sync::free` 内被调用的设备方法，必须 lock-free**
  （纯原子操作或直接返回），不得自取临界区或锁。
- 区内禁止：睡眠/等信号量、内存分配、调用厂商 API、格式化输出。
- 时长：微秒级。毫秒级操作只能走 C2 + actor。

> **移植方义务（临界区语义的核实）**：本规范只要求"不阻塞、可嵌套且嵌套安全、宿主与目标
> 语义一致、区内禁止睡眠/分配/厂商调用"。移植到任何 RTOS 时，必须核实其 critical section
> 实现（可重入性、SMP 行为、host mock 与真机差异），并在端口文档写明；未核实的实现不得
> 声称满足 R1。样本项目对应的 `sys::critical_section` 走厂商 `os_cs_enter/restore`，其可
> 重入性与 SMP 行为尚未经厂商确认——按本条处理。另：该仓 host mock 的临界区是**不可重入**的
> 进程锁（单层 enter/restore），与本节要求的"可嵌套且嵌套安全"不一致，拿它跑 host 测试前
> 必须先补深度计数——这正是 §10.4 第 8 项（R8 前置）要做的事。

### 4.6 自旋锁的使用条件

- 用于**跨核**共享的短临界区，且该状态不同时与同核 ISR 竞争。
- 同核 ISR 也会碰的状态，必须用 irqsave（关中断）版本——`sync::free` 已经这么做了；
  纯自旋锁在这种情况下会自旋等自己。
- 持锁期间不得阻塞、不得调用可能睡眠或调用厂商的函数。
- 无 CAS 的目标（rp2040/M0+）：单核空桩；SMP 移植时换 SIO 硬件锁。

### 4.7 可判规则

- **R1** 在 `sync::free` 内可被调用的方法，实现必须 lock-free：允许嵌套 `sync::free`
  （它可重入），但禁止自取任何其他锁/信号量/通道。
- **R2** **驱动的实现**（寄存器/状态机代码）内不得获取 Mutex/信号量/actor 通道；**能力方法**
  可以跨 actor 边界投递并等待回包，但该等待只允许发生在 C2。
- **R3** 厂商 API 只能在该设备的 owner 线程上调用——owner 可以是专门的 actor 线程，也可以是
  被约定为唯一调用者的任务（如 UI/LVGL 线程）。调用的方法等级限 **C2**，或标注为
  **非阻塞查询**的 **C1**（如 `Scanner::poll`、`PinEntry::poll`）：C1 内调厂商 API 必须
  不阻塞、不持锁、不睡眠。机器可判性由 §5.15.1 提供：**自有总线设备**的 owner =
  `BusArbiter::with_transaction` 的调用点；**厂商 SDK 设备**（不经 `BusDevice`）的 owner 见
  §5.15.1「厂商 SDK 设备」（`OWNER` 声明 + `claim_owner` 守卫）；`owner_of(name)` 只作诊断。
- **R4** C0 方法不得调用 C1/C2；C1 代码不得调用 C2。
- **R5** 设备状态用原子或单段 `sync::free` 保护；多步不变量不得横跨两次临界区。
- **R6** 事件通道用定长环 + 信号量，ISR 侧用 `post_isr`，不得在 C0 分配。
- **R7** 任何超时参数都必须显式传入（`Duration`），驱动不得内置无限等待。**例外**：
  `EventChannel::recv` 是生命周期有界等待——通道关闭即返回 `Cancelled`，不属本条的无限等待。
- **R8（机器判据）** R1/R4 必须由断言而非纪律保证：core 层提供 `in_critical_section() -> bool`
  （临界区深度 > 0），所有 C2 方法入口 `debug_assert!(!in_critical_section(), "C2 in sync::free")`；
  C0 方法**不得**接受 `&mut self`、不得返回带生命周期的借用。缺这两条时，C 级标注会随驱动
  更新而腐化（Linux 用 `might_sleep()`/lockdep 而非文档解决的就是这个问题）。

## 5. 接口规格

### 5.1 设备基座

```rust
/// 设备元数据基座：**无 `Sync` 上界**。供「不做 `dyn`、不进注册表」的专用设备使用（§5.2）。
pub trait DeviceBase {
    fn kind(&self) -> DeviceKind;   // 只作分类标签，不参与分发
}

/// 数据面设备的公共入口。`Sync` 是硬约束（`&'static dyn Device` 跨任务共享）。
pub trait Device: DeviceBase + Sync {}
```

> **方法接收者（规范）**：所有能力方法一律 `&self`。独占性由**句柄所有权 + `!Sync`** 表达，
> 不用 `&mut self`——否则同一能力要维护两套签名，且无法与 `&'static dyn` 数据面共存。
> 内部可变性按 §4 选择：`Cell`/原子/单段临界区（C0/C1）或 actor（C2）。

> **为什么拆基座（规范理由）**：能力契约必须能被**独占设备**实现——`open()` 得到的句柄、
> 持有 DMA 缓冲的设备、内部用 `Cell`/裸指针映射寄存器的实现，天然不是 `Sync`。要求所有
> 设备都带 `Sync` 上界，等于把这类设备排除在外，或逼实现用 `unsafe` 伪造证明。因此：
>
> - `DeviceBase`（无 Send/Sync 上界）= 专用能力的最小基座；
> - `Device: DeviceBase + Sync` = 只有需要 `&'static dyn` 跨任务共享的数据面与注册表路径才要求。
>
> **移植方义务**：独占设备**必须**用类型显式表达不共享（`!Sync` 或等价证明），并配
> `compile_fail` 用例；不允许用"调用约定"代替类型。样本项目按其现有独占性工作已做到
> 13/13（§10.3），仅是参考实现，不是规范依据。

### 5.2 能力发现的边界

- **数据面能力**（Stream / Block / Bus / Event / Switchable）保留 `as_*` + `Capability`
  泛型查找（`Capability` 机制），服务运行期按名注册的通用设备。
  其中 **Bus 分两层**：通用**字节事务** `BusDevice::transfer(&self, tx, rx)` 仍是数据面
  能力（`as_bus()` 返回 `Option<&dyn BusDevice>`，C2、仅 owner 调用）；**族专属命令**
  （PM/I2C、WLM/UART、IVR、Pinpad…）是各自的能力 trait，经 typed accessor 取用——
  **不存在全局 `BusCmd` 枚举**（那等于把 `Control(op, arg)` 换个类型复活）。
  `Switchable` 的 supertrait 是 `DeviceBase`。它是唯一横跨两侧的能力：经 `as_switchable`
  取到的是**数据面形态**（`Option<&(dyn Switchable + Sync)>`，可跨任务、可进 `static`）；
  `!Sync` 的独占句柄（DLED/GPIO）只用 typed accessor 调自己的方法，不进 `as_*`、不进注册表。
  若不写 `+ Sync`，`as_switchable` 拿到的 `&dyn Switchable` 跨不过任务边界——而 LED 开关正是
  最典型的跨任务调用（UI 任务取表、驱动 actor 执行）。
- **专用设备能力**（Card / Display / Pinpad / Scan / Wifi / Ble / Printer / Dled / …）
  **不进 `Device` 的 `as_*`**：专用设备通常经 typed accessor/静态单例取用（如
  `CardReader::instance()`），调用方手里没有 `&dyn Device`；强塞进 `Device` 只会让 trait
  膨胀到二十个方法，且违反「新增 `as_*` 必须有真实实现」的规矩。
- **专用设备能力的 supertrait 是 `DeviceBase`（不要求 `Sync`）**：它们只经 typed accessor
  使用、从不进 `as_*`/注册表，因此不需要 `Sync`。对齐修订 2026-10-29（§10 第 1 项）。
- `DeviceKind` 按需扩展（Stream/Block/Bus/Control/Display/Card/Net/Input/…），
  **永远不参与能力分发**。

### 5.3 数据面能力（保留并标注上下文）

```rust
pub trait StreamDevice: Device {
    fn available(&self) -> usize;                                        // C0
    fn register_waiter(&self, waiter: usize) -> Result<(), DeviceError>; // C0
    fn read(&self, buf: &mut [u8]) -> Result<usize, DeviceError>;        // C1
    fn write(&self, buf: &[u8]) -> Result<usize, DeviceError>;           // C1
    fn write_all(&self, buf: &[u8]) -> Result<(), DeviceError>;          // C1
}

pub trait BlockDevice: Device {                                          // 全部 C2
    fn sector_size(&self) -> u64;
    fn sector_count(&self) -> u64;
    fn read_sector(&self, no: u64, buf: &mut [u8]) -> Result<(), DeviceError>;
    fn write_sector(&self, no: u64, buf: &[u8]) -> Result<(), DeviceError>;
}

pub trait EventDevice: Device {
    fn register_waiter(&self, waiter: usize) -> Result<(), DeviceError>; // C0
    fn wake(&self);                                                      // C0
}

pub trait BusDevice: Device {
    /// 一次字节事务：发送 `tx`，同时把读入写入 `rx`。**C2、仅 owner 任务调用**。
    fn transfer(&self, tx: &[u8], rx: &mut [u8]) -> Result<(), DeviceError>;
}

/// 开关量能力：数据面设备与专用设备都可实现；**不要求 `Sync`**（DLED/GPIO 常为独占句柄）。
pub trait Switchable: DeviceBase {
    fn on(&self) -> Result<(), DeviceError>;      // C2（I2C 扩展器可能阻塞）
    fn off(&self) -> Result<(), DeviceError>;     // C2
    fn toggle(&self) -> Result<(), DeviceError>;  // C2
}
```

`read_blocking` 保留为 `StreamDevice + EventDevice` 的 C2 适配器。
**共享总线的仲裁与寄存器访问助手由 core 层提供（§5.15）**；`BusDevice` 仍是唯一的总线能力面，
`RegMap` 只是它的 consumer 侧助手。

> **总线（规范）**：`BusDevice::transfer(&self, tx, rx)` 是**通用字节事务**能力（I2C/SPI 等），
> 签名不含族命令，因此不存在"万能控制面"问题；约束是 **C2、仅 owner 任务调用**，共享总线
> 由 owner 串行化（§4.4）。族专属命令（PM/WLM/IVR/Pinpad）各立 typed trait，
> **不聚合成全局 `BusCmd`**（§5.9）。

### 5.4 专用设备能力（签名示例）

> **对齐修订（2026-10-29）**：本节 trait 的 supertrait 由 `Device` 改为 `DeviceBase`——它们不做
> `dyn`、不进注册表，不应继承 `Device` 的 `Sync` 上界（§10 第 1 项）。
>
> **本节的卡/PIN，与其余设备中的密钥注入/SAM/GATT，共享一种形状：Transaction / Session**——
> **请求-应答 + 会话句柄 + 显式超时 + 可取消**，外加独占某些物理资源。满足这四条的设备就属于
> 事务面；在卡/PIN 类产品里它是核心形态，但并非唯一形态。**不要往控制面里塞**——那正是
> v2/v3 要消灭的万能控制面。
> 同节示例里的 `Scanner` 属于 PollingAsync、`WifiDevice` 属于 EventStream——**形状可以叠加**，
> 一台设备可以同时是 Transaction + PollingAsync（PIN 就是）。

```rust

    fn apdu(&self, card: CardId, cmd: &[u8], timeout: Duration)

    fn power_down(&self, card: CardId) -> Result<(), DeviceError>;                     // C2
}

/// 扫码：轮询异步，天然可取消。

    fn start(&self, mode: ScanMode) -> Result<ScanOp, DeviceError>;     // C2
    fn poll(&self, op: ScanOp) -> Poll<ScanOutcome>;                    // C1

    fn connect(&self, cfg: &NetCfg, timeout: Duration) -> Result<(), DeviceError>; // C2

/// PIN：同步密码运算 + 带会话的异步输入。
```

### 5.5 执行模型骨架（只作分类，不用于 `dyn`）

```rust
pub trait SyncOp        { type Outcome; }
pub trait PollingAsyncOp{ type Op: Copy; type Outcome; }
pub trait EventSource   { type Event: Copy; }
pub trait TransactionOp { type Session: Copy; }   // 请求-应答 + 会话
```

规则：关联类型只出现在这四条**分类骨架**里；任何要用于 `&dyn` 的能力 trait 必须把
`Outcome`/`Event`/句柄写成**具体类型**（如 `ScanOutcome`、`WifiEvent`、`ScanOp`）。

**返回形状的约定**：① 同步短操作 → `Result<T, DeviceError>`；② 会话轮询 → `Poll<Outcome>`；
③ 可判业务结果 → `Outcome` 枚举；④ `Err(Timeout)` 只用于传输层；⑤ 同步方法「窗口内无结果」
用 `Ok(None)`（如 `CardReader::poll_select`），不是错误。**例外**：已有 `try_read`/事件通道旁路的
设备（如 `Keyboard::read_key`、`WifiDevice::scan`）用 `Err(Timeout)` 表示窗口耗尽，`Ok(None)` 留给
「必须区分『没有』和『超时』」的取卡/选卡类调用。

事务面（Transaction / Session）的**特征清单**（描述性，用于归类与自查，不是规范判定式）：
**① 有会话句柄**（`PinSession`/`CardId`/`ConnHandle`）**② 每次操作有显式超时**
**③ 可取消** **④ 独占一份物理资源**（卡槽、安全芯片、连接）。

> 「缺一条就不是 Transaction」不构成规范条款：形状可以叠加（见本节前言），归类只影响写在哪一节，
> 不影响接口形状。

### 5.6 生命周期

> **对齐修订（2026-10-29）**：`Openable` 改继承 `DeviceBase`；并记录**两种生命周期形状并存**：
> 常驻设备用 `open(&self)` 做状态迁移（本节），独占句柄用 `open() -> Result<Self>` 构造 +
> `Drop` 归还（外部项目）。`Openable` 只描述前者，后者不实现本 trait（§10 第 8 项）。

```rust
pub trait Openable: DeviceBase {
    fn open(&self) -> Result<(), DeviceError>;  // C2；重复 open → Busy
    fn close(&self);                            // C2；幂等
    fn is_open(&self) -> bool;                  // C1
}
```

独占外设可提供 `Drop` 凭证（`Owned<'a, T>`）在析构时 close；close 失败只能记日志——
析构不能返回错误。未 open 调用业务方法返回 `InvalidInput`。
`is_open` **只作诊断，不作同步判据**：open/close 执行期间它可能瞬时不准。

**失败路径（规范）**——`close` 幂等只是其中一小半：

- **`open` 失败必须回到「完全未 open」状态**：半初始化取得的时钟/中断/GPIO/缓冲在同一函数内撤销，
  且失败后再次 `open` 必须能成功（可重试），不允许留下「开了一半」的中间态。
- **`Recoverable::reset` 与 owner 队列**：reset 期间到达的命令**丢弃并回 `Cancelled`**（不排队等 reset
  完成——复位后执行过期命令比丢命令危险）；reset 结束后设备状态 = `close` 后状态，业务方自行重新 `open`。
- **`Drop` 顺序**：先停 owner（拒收新命令、在途命令回 `Cancelled`）→ close → 释放缓冲。析构不能
  返回错误，失败只记日志（见本节上一段）。

### 5.7 错误与结果

```rust
pub enum DeviceError {
    // —— 注册期 ——
    Duplicate,        // 注册名重复
    Full,             // 定长容器已满（注册表 / 事件环）
    // —— 能力 / 参数 ——
    Unsupported,      // 设备没有这个能力（**只用于能力级**；op 级不支持用 InvalidInput）
    InvalidInput,     // 参数非法 / 未 open / 句柄失效 / 未知 op
    Busy,             // 设备被占用 / 重复 open / 单订阅设备第二次 events()
    // —— 操作期 ——
    Timeout,          // 传输层超时（业务「无结果」走 Outcome / Ok(None)）
    Cancelled,        // 被取消 / 通道已关闭
    Io,               // 底层 I/O 失败
    UnexpectedEof,    // 读提前到卷尾（文件系统适配）
    WriteZero,        // write_all 零进度
    Vendor { module: u16, code: i32 },  // 厂商原始错误码，按模块分段
}
```

- **业务结果走 `Ok(Outcome)`**：扫码超时是 `ScanOutcome::Timeout`，不是 `DeviceError`。
- **注册错误与操作错误同枚举**：统一错误面，上层一个 `Result` 同时处理注册与操作；移植方若
  另有注册错误类型，在边界映射（映射示例见 §10.5）。
- **`Unsupported` 语义收窄**：只表示「本设备没有这个能力」（`as_*` 返回 `None`）；`IoCtl`
  的未知 op、设备内不支持的子命令一律 `InvalidInput`。
- **体积取舍**：`Vendor{module,code}` 把 `DeviceError` 从 1 字节抬到 8+ 字节，所有
  `Result<T, DeviceError>` 跟着变大。本规范取可诊断性优先；在意体积的端口可改
  `Vendor(u16)` 或标 `#[non_exhaustive]`。
- 厂商负码只增不减地透传进 `Vendor`，上层可诊断，不参与业务分支。
- **移植方义务**：端口必须提供 `DeviceError → 平台错误` 的映射，且不得丢失
  `Vendor{module,code}` 的原始码；映射表属于端口文档（样本项目的映射见 §10.5），
  不属于本规范。

### 5.8 事件通道

```rust
/// 定长环 + 信号量 + 唤醒；**零分配**，可用于无堆目标。
pub struct EventChannel<T, const N: usize> { /* ... */ }

impl<T: Copy, const N: usize> EventChannel<T, N> {
    pub const fn new() -> Self;                                  // 无分配、可 const 构造
    pub fn try_recv(&self) -> Option<T>;                         // C1
    pub fn recv(&self) -> Result<T, DeviceError>;                // C2；通道关闭 → Cancelled
    pub fn recv_timeout(&self, timeout: Duration) -> Result<T, DeviceError>; // C2；超时 → Timeout
    pub fn post(&self, v: T) -> Result<(), DeviceError>;         // C1/C2（厂商回调线程）；满 → Full
    pub fn post_isr(&self, v: T) -> Result<(), DeviceError>;     // C0（硬件 ISR）；满 → Full
    pub fn overflow_count(&self) -> usize;                       // C1；累计 post 失败次数（诊断）
}
```

`EventDevice` 只负责「字节流有数据了」的唤醒边沿；多事件设备一律用 `EventChannel`。

实现约束（规范）：

- **不复用 `sync::Queue` / `sync::Semaphore`**：两者都经 `Arc<RefCell<..>>` 堆分配
  （`queue.rs:20`、`semaphore.rs:23-25`），与零分配矛盾；`EventChannel` 自实现。
- **存储用 `[MaybeUninit<T>; N]`**（`[const { MaybeUninit::uninit() }; N]`，nightly），配
  head/tail `AtomicUsize` + **单等待者** `AtomicUsize`。多任务并发 `recv` 时，第二个返回
  `Busy`（与 `EventDevice` 的单等待者契约一致）。
- **代码不约束 `T: Copy`**：上面的签名是最小可用约束；实现允许非 `POD` 事件（如 `Vec<u8>`），
  代价是**必须**配 `impl Drop` 把环里未消费的事件排空析构（否则纯泄漏）。
- **`recv_timeout` 的超时是 `sleep_ms` 分片轮询，不是真阻塞**（内核原语缺口，已记入 §10 第 11 项）：
  `Task::wakeup` 只对 `State::Suspended` 生效，而 `sleep_ms` 走 `State::Blocked` + 延时队列
  （`task.rs` 两条不同的挂起通道），所以目前没有「延时 + IPC 唤醒」双登记的 timed-block 原语。
  可见差异：超时精度 = tick、事件到达的唤醒延迟 ≤ 1 tick；期间仍占单订阅登记位（RAII），
  并发 `recv` 照常 `Busy`。亚毫秒超时按 **1 tick** 计——截断为 0 会静默退化成「不等待」。

**满时语义（规范）**——环满一律失败，**不静默丢最旧**（事件"消失"是最难查的一类缺陷）：

- **`post` 满 → `Err(Full)`**：调用方（任务上下文）自行决定阻塞重试或丢弃；已入队事件不被覆盖。
- **`post_isr` 满 → `Err(Full)`，但 ISR 不重试、不记日志**：容量必须由**构造**保证（≥ 该设备
  一轮 ISR 的最坏事件数）；ISR 里满就说明容量定小了，属设计缺陷，用 `overflow_count()` 暴露。
- **`overflow_count()`（C1）**：累计 `post`/`post_isr` 失败次数；host 单测用它断言"容量足够"，
  现场用它判断"事件是否丢过"。
- **auto-trait**：字段只有 `AtomicUsize` + `[MaybeUninit<T>; N]`，故 `T: Copy + Send` 时
  `unsafe impl Send / Sync`（等待者由 `sync::free` 串行化，同 `Semaphore` 的纪律）；
  因此 `events()` 的返回值可以交给另一个任务消费。

订阅语义（必须写死，避免各实现各写各的）：

- **默认单订阅**：同一设备第二次 `events()` 返回 `Err(Busy)`。设备只有一个事件源，
  多消费者请在应用层用广播/汇合通道分发。
- 确需多消费者的设备（如键盘：UI 与业务都要）**在能力 trait 的文档里显式声明**，
  并返回广播通道；未声明一律按单订阅处理。
- **状态语义**：设备未连接/未 open 时调用 `events()` 返回通道但不投递事件；`disconnect`/`close`
  后通道关闭（`recv` → `Cancelled`）。

多订阅（`Broadcast<T, const N: usize>`）——**按需实现，不阻塞 §8**：

- 首批只用于键盘（§5.4）。最小形状：`subscribe() -> Result<Subscription, DeviceError>`
  （订阅者数超限 → `Full`）、`Subscription::try_recv/recv/recv_timeout`；
  `post`/`post_isr` 满时语义与 `EventChannel` **相同**（`Full`，不丢最旧）。
- **慢订阅者不阻塞发布者**；若某订阅者游标落后到被覆盖，策略**必须显式选定并写进实现文档**：
  允许「跳过并计数」，**禁止静默**。
- 未落地前，键盘允许退回上一条的默认单订阅（应用层汇合）。

### 5.9 总线：通用事务 + 族专属命令

总线分两类，**都不使用全局命令枚举**：

1. **通用字节事务**（I2C/SPI/位流）：`BusDevice::transfer(&self, tx, rx)`（§5.3）。C2、仅
   owner 调用；共享总线由 owner 串行化，驱动内部零锁。
2. **族专属命令**（PM/I2C、WLM/UART、IVR、Pinpad…）：每个族一个 typed trait（如
   `IvrBus::play(&self, ...)`、`PmBus::set_voltage(&self, ...)`），经 typed accessor 取用；
   需要异步请求-应答的，用 §5.4 的 Transaction 形状（会话 + 超时 + 取消），而不是一个
   `call(cmd)` 大枚举。

> **为什么不做全局 `BusCmd`**：把各族命令聚合成一个对象安全的 `call(cmd)`，就是
> `Control(op, arg)` 换皮——v2/v3 的整个论证（类型化能力替代万能 op）会因此失效。
> 样本项目的 `BusCmd` 全域枚举是 Phase 0 占位（无载荷）；按本规范拆成族专属 trait。

族总线 trait 的最小形状（以 IVR 为例）：

```rust
pub trait IvrBus: DeviceBase {
    fn play(&self, name: &str, format: u32, timeout: Duration) -> Result<(), DeviceError>; // C2
    fn stop(&self) -> Result<(), DeviceError>;                                             // C2
    fn events(&self) -> Result<EventChannel<IvrEvent, 8>, DeviceError>;                    // C2
}
```

owner 任务串行执行，驱动不持有任何锁。**同一总线的多器件共享与多段事务不被打断，由 core 层
`BusArbiter::with_transaction` 保证（§5.15.1）**；I2C/SPI 器件不要手拼 `tx/rx`，用 `RegMap`（§5.15.2）。

### 5.10 逃生舱

```rust
pub trait IoCtl: DeviceBase {
    /// # Safety
    /// `arg` 的类型/大小/对齐/生命周期由 `op` 的厂商契约决定；不得留存。
    unsafe fn ioctl_raw(&self, op: u32, arg: *mut core::ffi::c_void)
        -> Result<isize, DeviceError>;   // C2
}
```

- **每设备一个**：逃生舱是设备能力的一部分，不做全局值类型 `Cmd`/`Reply` 渠道（样本项目
  的 7 个设备都落在这个形状，见 §10.3）。
- **supertrait 是 `DeviceBase`（不要求 `Sync`）**：逃生舱挂在专用设备上（卡/音频/键盘/打印机/
  磁条卡/数码管），而外部项目的这些句柄都是 `!Sync` 独占句柄。对齐修订 2026-10-29。
- `op` 是 **u32**（厂商 `ulong cmd`）。
- 实现数必须为 0 或对应真实厂商命令；禁止为演示造桩。
- 这是唯一允许「返回值多义」的地方；正文必须明说这是刻意的代价。

### 5.11 动态句柄

`ConnHandle` / `PinSession` / `ScanOp` / `CardId` / `Screen` 等是**能力 trait 内部的具体
`Copy` 句柄**，永远不是 `Device`。驱动必须校验句柄（失效 → `InvalidInput`），并保证
句柄不跨设备复用。

### 5.12 【附录·非规范】预留数据面（帧 / 采样 / 文本）——**未实现，不写桩**

> 本节不是规范条款（见 `docs/设备驱动抽象层v3-设计权衡.md` §2.1）。除 `FrameSink` 外，其余
> trait 无消费者，不进入 §8 验收，也不得据此写桩。

帧/采样/文本是通用嵌入式的基本数据面；本仓当前没有这些驱动。按「能力要么真能，
要么不存在」，本节只记形状，不写实现、不写 `Unsupported` 桩。

```rust
pub trait FrameSource: DeviceBase {   // camera / ToF
    fn next_frame(&self, timeout: Duration) -> Result<Option<FrameDesc>, DeviceError>; // C2
    fn read_frame_into(&self, buf: &mut [u8]) -> Result<usize, DeviceError>;           // C2
    fn format(&self) -> FrameFormat;                                                   // C1
}
pub trait FrameSink: DeviceBase {     // display 的像素面
    fn submit(&self, region: Rect, data: &[u8]) -> Result<(), DeviceError>;            // C2
}
pub trait SampleSource: DeviceBase {  // mic / I2S 入
    fn format(&self) -> SampleFormat;                                                    // C1
    fn read_samples(&self, out: &mut [i16], timeout: Duration) -> Result<usize, DeviceError>; // C2
}
pub trait SampleSink: DeviceBase {    // speaker / I2S 出
    fn write_samples(&self, data: &[i16], timeout: Duration) -> Result<usize, DeviceError>;    // C2
}
pub trait TextSink: DeviceBase {      // 数码管
    fn show(&self, text: &str) -> Result<(), DeviceError>;   // C2
    fn clear(&self) -> Result<(), DeviceError>;              // C2
}
```

约束：

1. **方向显式**：源/汇分开——display 是**汇**，camera 是**源**；speaker 是汇，mic 是源。
2. **不要塞进 `StreamDevice`**：PCM 当字节流会丢采样率/位深/通道；帧当字节流会丢边界与时间戳。
   Linux 为此分了 ALSA / V4L2 / IIO 三个子系统。采样面必须像帧面一样带
   `SampleFormat { rate_hz, bits, channels }`，不得把格式写死成 S16 单声道。
3. `FrameDesc` 只携值字段（格式/序号/时间戳），像素经 `read_frame_into` 另取——与 `scan`
   解码回调「回调内只拷值、载荷另取」同一条纪律。
4. `Display` 可以**同时**实现 `FrameSink`（其 `flush` 即子集），但保留自己的文本/背光方法：
   轴是能力，不是设备分类。
5. 首个真实驱动落地前，这些 trait 不实现、不导出；`pos5-hwtest` 的 `camera_open/scan`
   是应用侧探针，不算实现。

### 5.13 绑定方式（三种形态）

| 形态 | 适用 | 边界 |
|---|---|---|
| 编译期清单（名字 → 实例） | 生产路径；多实例用 `(总线, 端口, 地址/片选)` 区分 | 只解决**绑定**，不解决能力；**动态句柄（`ConnHandle`/`PinSession`/`ScanOp`/`CardId`）永不进清单** |
| 运行期表（`DriverRegistry`） | 热插拔：USB / SD / SIM；教学演示 | 不是默认路径；产品侧优先编译期绑定 |
| 厂商全局函数 | 没有总线 ID 的设备（`Scan_Open`、`Pinpad_*`、`Printer_*`） | 清单在这里只是「名字 → 函数表」，**不要假装是设备树匹配** |

> **对齐修订（2026-10-29）**：外部报告前一版说「两个仓都没有热插拔」是错的——Xtask 有
> `src/usb/{otg,mock}` 与枚举用例，产品侧 `src/sys` 也接了 USB。**BOM 固定 ≠ 设备常在**，
> 运行期表保留（降为子集能力）。

**初始化顺序（规范）**：

- 静态初始化顺序 **= 清单顺序**；靠后的条目可以依赖靠前的条目，反向依赖是错误。
- 依赖失败 **立即 panic 并打出依赖名**（如 `"i2c0 not initialized for panel"`）。
- **不引入延迟 probe**：本仓无模块加载/无 `EPROBE_DEFER` 对应的复杂度，需要它的场景应当重排清单。
- 运行期表（热插拔）的条目在插入时自身完成初始化，不参与清单顺序；其依赖必须已就绪，
  否则插入失败返回 `InvalidInput`。

### 5.14 【附录·非规范】前瞻能力（只记形状，不实现、不写桩）

> 本节不是规范条款（见 `docs/设备驱动抽象层v3-设计权衡.md` §2.1）。仅两个条目具有规范地位：
> `DmaBuffer`（DMA 对齐/所有权是安全属性）与 `Recoverable`（其 reset 语义见 §5.6「失败路径」）；
> `PowerManaged`/`AsyncOp` 只记录形状，不进入 §8 验收。

通用嵌入式还需要的五类能力。本版**只定形状**，首个真实驱动落地时再实现；在此之前不导出、
不写 `Unsupported` 桩。

```rust
/// 电源管理：设备树/时钟门控/低功耗。suspend 只能在 C2 调用；resume 后必须重建设备状态。
pub trait PowerManaged: DeviceBase {
    fn suspend(&self) -> Result<(), DeviceError>;   // C2，幂等
    fn resume(&self) -> Result<(), DeviceError>;    // C2，幂等
}

/// 异步适配：把 PollingAsync/EventChannel 映射成 Future；不定义第二套 async trait。
pub trait AsyncOp {                                 // 分类骨架，不用于 dyn
    type Outcome;
    type Future<'a>: core::future::Future<Output = Result<Self::Outcome, DeviceError>>;
}

/// DMA 缓冲：所有权 + 对齐 + cache 维护责任，禁止把普通切片交给 DMA。
pub struct DmaBuffer<const N: usize> { /* 对齐缓冲 + 已初始化长度 */ }

/// 热插拔/故障恢复：复位与重新初始化；枚举仍由绑定层负责（§5.13）。
pub trait Recoverable: DeviceBase {
    fn reset(&self) -> Result<(), DeviceError>;     // C2
}
```

- **时间戳**：所有帧/采样必须带单调时间戳（`Instant` 或设备时钟），供音视频/传感器融合对齐。
- **安全边界**：安全芯（SE/TrustZone）只经专属 trait 暴露，不并入通用数据面；密钥与 PIN
  路径不得出现在 `Debug`/日志里。
- **无分配目标**：事件通道与批量读取必须提供定长/借用缓冲版本；需要 `Vec` 的接口（如
  WiFi 扫描列表）必须同时给出 `_into(&mut [T])` 变体。

> 电源管理与异步适配**不阻塞** v3 实施；DMA 缓冲在首个 DMA 设备出现前不落地，
> 且 `ioctl_raw` 不得承载 DMA 缓冲的生命周期。

### 5.15 core 层（框架层）职责

> 本节补的是「规范 + 驱动 + 应用」之间缺的那一层。Linux 的对应物是 driver core / `i2c_adapter` /
> `regmap`——**状态与仲裁在 core，驱动只提供 ops**。本仓的落点是 `src/device/{mod,caps,event,bus,regmap}.rs`
> （§8 步骤 2）。决策记录见 `docs/设备驱动抽象层v3-设计权衡.md` §3.1。

三条职责：

1. **拥有共享资源的仲裁**：同一总线上的所有事务经一个 core 类型排队，调用方不自行约定「谁先」。
2. **拥有实例生命周期与注册**：`register → find → owner 分配`，以及 close/remove 的顺序。
3. **提供 consumer 侧 API**：驱动只实现 ops 与能力 trait，取用侧走 core 的 typed accessor。

#### 5.15.1 共享总线仲裁

```rust
/// 共享总线仲裁器：core 层持有的**具体类型**（不是 trait object）。
/// 说明：`with_transaction` 是泛型方法，带泛型方法的 trait 不 object-safe；
/// core 只有一个实现，无需 `dyn BusArbiter`，因此用 struct 而不是 trait。
pub struct BusArbiter { /* 每总线一个 owner/队列 */ }

impl BusArbiter {
    pub fn with_transaction<R>(&self, f: impl FnOnce(&dyn BusDevice) -> R) -> R; // C2
    pub fn owner_of(&self, bus: &str) -> Option<&'static str>;                   // C1；诊断
}
```

- **调用者即 owner**：owner 不再靠文档约定或外部归属表，而是 `with_transaction` 的调用点；
  同一总线上出现第二个并发调用者就是设计错误（host 侧用断言暴露）。
- **任何 `BusDevice::transfer` 都必须在 `with_transaction` 内**调用；目录外直接调视为违规。
- **多段事务必须落在同一个 `with_transaction` 内**（典型：写寄存器地址 + 读数据），
  否则中间可被同总线上的其他器件插入。
- 不引入新的锁语义：仍由 `sync::free`/自旋 + owner 任务构成（§4.1）；仲裁器只负责「序列不被打断」
  与「跨器件共享同一总线时的互斥」。

**厂商 SDK 设备（不经 `BusDevice`，总线由厂商库内部持有）**

「调用者即 owner」只覆盖经自有总线的设备。厂商 SDK 设备（样本项目的 12 个句柄全部经
`cris_*`/`ql_*`，不经 `BusDevice::transfer`）另立一条：

- **owner 由声明给出**：设备类型提供 `const OWNER: &'static str`（或由 core 的设备表登记），
  不依赖调用点推断；
- **claim 守卫**：core 提供 `claim_owner(dev, task) -> Result<OwnerGuard, DeviceError>`；
  同一设备第二次 claim → `Busy`，`OwnerGuard::drop` 释放；
- **dev/host 断言**：所有 C2 入口 `debug_assert_eq!(owner_of(NAME), Some(current_task()))`
  （复用 R8 的断言机制；release 剔除，零开销）；
- **`OWNER` 是名字，不是任务句柄**：任务是运行期 spawn 的，句柄进不了 `const`，声明只给
  诊断/断言用的名字，真正的绑定由 `claim_owner` 在 init 阶段完成。Xtask 侧没有 `TaskId`，
  任务身份就是 `xworker.rs:29` 的 `current_ptr() -> *mut Task`，`claim_owner` 的参数直接用这个指针。
- **诚实边界**：release 构建里**没有**"这次调用是否来自 owner"的检查——执行机制是"单份 claim"
  （第二次立刻 `Busy`），检测机制是 dev/host 断言。不得暗示 release 下也有运行时校验。
- `with_transaction` 只覆盖经自有总线的设备——样本项目当前为 0 个（等 ToF/camera 等
  自有总线驱动落地）。

两类 owner 并列、不混用：自有总线看 `with_transaction` 调用点，厂商 SDK 看 `OWNER` 声明 +
claim 守卫。验收（host 两条）：① 同一设备两次 `claim_owner` → 第二次 `Busy`；② 非 owner
任务调用 C2 方法 → dev 构建断言触发。

#### 5.15.2 寄存器访问助手 `RegMap`

```rust
/// I2C/SPI 器件的寄存器访问助手：地址宽度/字节序/缓存随实例定制，驱动不再手拼 tx/rx。
pub struct RegMap<B: BusDevice> { /* bus, addr, addr_bits, big_endian, cache */ }

impl<B: BusDevice> RegMap<B> {
    pub fn read(&self, reg: u32) -> Result<u32, DeviceError>;                              // C2
    pub fn write(&self, reg: u32, val: u32) -> Result<(), DeviceError>;                    // C2
    pub fn update_bits(&self, reg: u32, mask: u32, val: u32) -> Result<(), DeviceError>;   // C2
    pub fn poll_bits(&self, reg: u32, mask: u32, expect: u32, timeout: Duration)
        -> Result<(), DeviceError>;                                                        // C2
}
```

- 不变量：`update_bits` 的读-改-写在**一个** `with_transaction` 内完成，否则并发写会丢位。
- `poll_bits` 的等待走 `Duration`，不得内置无限等待（R7），超时回 `Timeout`。
- `RegMap` 是 `BusDevice` 的 **consumer 侧助手**：不新增能力、不进 `as_*`、不进注册表。

### 8.3 flash 预算与反膨胀规则

嵌入式存储有限，本层的存在必须能交代自己的字节数。实测方法：`thumbv7m-none-eabi`，
`-C opt-level=z -C lto=fat -C panic=abort`，6 个设备 × 3 个方法 × 2 个调用点，
**同一工作量只换形态**，基线为空 `entry`：

> **微基准：`thumbv7m`、18 个方法（6 设备 × 3）；不代表样本项目的 13 句柄 / ~200 方法面。**

| 形态 | .text | 相对直接调用 | 每设备摊销 |
|---|---|---|---|
| 空基线 | 162255 B | — | — |
| 具体类型直接调用 | 162615 B | 基准 | ~60 B |
| 泛型（单实例化） | 162615 B | **+0 B** | ~60 B |
| `&dyn` 能力查找 | 163465 B | +850 B | ~140 B |
| `&dyn` + 名字注册表 + core 层 `RegMap` | 164294 B | +1679 B | ~340 B |

读法：

- **能力 trait 本身几乎不占 flash**——泛型单实例化与直接调用同码；`dyn` 的增量来自
  虚表（4 B/方法/设备）、名字表与「`dyn` 阻碍内联」。
- **绝对量级是百字节~KB**：上表整个 v3 能力面 + core 层 ≈ 1.7 KB，与 LVGL/字体/协议栈
  （十 KB~百 KB）不同量级。**限制存储的不是这层抽象，是图形与协议栈。**
- **真正会膨胀的是单态化**：泛型一旦被 N 个设备各实例化一次，代码就是 N 份。

反膨胀规则（实施时逐条勾）：

- **`EventChannel<T, N>` 按 `(T, N)` 单态化**：代码份数 = 事件类型数 × 容量组合。同类事件先归一
  （如驱动内映射成 `u16` 载荷），容量**默认 8**；确需调整须在设备文档写明理由，并在
  反膨胀表登记 `(T, N)` 组合（禁止随手自定义）。
- **core 层用 `dyn`，驱动实现不加类型参数**：`RegMap`/仲裁器持 `&dyn BusDevice`（一份代码）；
  驱动自身除 `const N` 外不引入泛型参数。
- **驱动内禁止带格式串的 `panic!`/`unwrap`/`assert!`**：一次 `{}` 会反引 `core::fmt`（数 KB 级）。
  出错只回 `DeviceError`；格式化只允许出现在 core 层的 `debug_assert!`（静态字符串）。
- **日志走 feature gate**（`rtt_log`/`stdout_log`），驱动不留裸 `log::info!`。
- **注册表名字用 `&'static str` 直接比，禁止 `alloc::String`/`format!`**；条目 ≥ 6 时用 `match`
  或编译期 hash 常量，避免线性比较链。
- **字体/帧缓冲不进本层**：`FrameSink` 只持引用，像素缓存归 `Display` 实例。

**门禁落地（防膨胀不是靠人记得）**：`ci/check_size.py` 直接解 ELF 段表（不依赖 `size`/`objdump`——
`arm-none-eabi-size` 读不了 riscv 产物），基线存 `ci/size-baseline.txt`，在 `ci/gate.sh` 第 3 步对
6 个剖面执行：`driver`（驱动能力面）/ `fatfs` / `net_echo` / `qemu_pingpong` / `multitask_ch583`（256K flash 板）
/ `multitask_ch572`（无 A 扩展、12K SRAM）。阈值 flash +5%/+256 B、RAM +4%/+128 B（`.stack` 预留单独报出，
不计入门禁，否则调栈会误报），超了当场红并列出最大段。只有**有意的功能增量**才用
`python3 ci/check_size.py <名字> <elf> --update` 刷基线，并在提交信息里写明增长了什么。

### 10.2 一句话存档

本轮讨论最值钱的结论不是"六轴"，而是这两个二分：

- **Linux = 子系统（数据面 + 服务语义） + 总线枚举（发现）**；
- **本项目设备的核心形态是 Transaction / Session，不是媒体流**——媒体流是少数派。

前者解释了 Xtask 缺的是「服务语义」那一半（等待队列、多消费者、per-open 状态），不只是少几个类目；
后者解释了为什么照抄 Linux 的媒体子系统会把卡/PIN/密钥全塞回 `Control`——那正是 v2/v3 要消灭的东西。
