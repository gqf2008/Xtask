# 设备驱动抽象层重设计

> 关联书稿：第 20 章《驱动抽象层》

## 1. 背景与问题

现有驱动抽象层有两个并存形态：

- `drv::DriverRegistry`：运行期注册表，`DeviceApi` 枚举承载三类设备
  （`Led` / `Uart` / `Bd`），配套 `LedDevice` / `UartDevice` / `BdDevice` trait。
- `drv_static::DeviceTable`：编译期设备清单，`DeviceDef + DeviceSlot + device_list!`，
  模拟 Zephyr 的静态设备表。

主要问题：

1. **分类被锁死在枚举里**：新增设备类要同时改 `DeviceApi`、三个 trait、
   注册表的便捷方法，扩展成本高。
2. **“控制面”没有独立表达**：LED 这种纯控制设备、以及 UART/SD 的配置参数
   （波特率、块大小、厂商命令等）没有统一模型。
3. **字节流接口是自定义的**：`rx_len/read_byte/write_all` 与生态里的
   `Read/Write` 形状不一致，不利于接入第三方驱动。
4. **`DeviceApi` 枚举与 `DeviceKind` 语义重叠**：分类标签和可调用能力
   混在一个枚举里，既承担“是什么”，又承担“能干什么”。

## 2. 目标

- 以 **`Device` 为顶层抽象**，用 **`DeviceKind` 做分类标签**。
- 用 **首批四个能力 trait** 表达通用外设：`StreamDevice`、`BlockDevice`、`Control`、`BusDevice`；其余专属 trait（`NetDevice / DisplayDevice / CanDevice / GpioDevice / PwmDevice / HidDevice / FrameDevice / TimerDevice / RtcDevice / WdgDevice / DmaDevice`）按需扩展；音频 / ADC / DAC 收敛为 `StreamDevice + Control`。
  - 字节流设备：`StreamDevice`
  - 块设备：`BlockDevice`
  - 控制面 / 控制指令参数：`Control`
  - 总线设备：`BusDevice`
- 四者**继承 `Device`**，形成统一的顶层入口。
- 注册表 / 静态清单只与顶层 `Device` 打交道，不感知具体设备类。
- 能覆盖当前外设（UART / LED / SD），并为后续外设（PWM、I2C、SPI 等）
  保留平滑扩展位。

## 3. 核心模型

### 3.1 分类标签 `DeviceKind`

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum DeviceKind {
    /// 字节流设备：UART / USB CDC / BLE 数据通道……
    Stream,
    /// 块设备：SD 卡 / Flash / 内存盘……
    Block,
    /// 纯控制设备：LED / PWM / GPIO 控制面……
    Control,
    /// 总线设备：SPI 全双工同步事务……
    Bus,
    // 未来可扩展：Timer / Pwm / Gpio / Display / Can……
}
```

`DeviceKind` 只回答“它是什么”，不携带任何能力。

> `kind()` 的消费方是诊断日志 / 设备清单 / 板级匹配，不参与能力分发（能力走 `as_*`）；复合设备以“主类”报告 `kind`。

### 3.2 顶层抽象 `Device`

```rust
/// 所有设备的公共入口
pub trait Device: Sync {
    /// 设备类别
    fn kind(&self) -> DeviceKind;

    /// 取字节流能力，不支持返回 None
    fn as_stream(&self) -> Option<&dyn StreamDevice> { None }

    /// 取块设备能力，不支持返回 None
    fn as_block(&self) -> Option<&dyn BlockDevice> { None }

    /// 取控制面能力，不支持返回 None
    fn as_control(&self) -> Option<&dyn Control> { None }

    /// 取总线能力，不支持返回 None
    fn as_bus(&self) -> Option<&dyn BusDevice> { None }

    /// 取事件/唤醒能力，不支持返回 None
    fn as_event(&self) -> Option<&dyn EventDevice> { None }
}
```

说明：

- 注册表只持有 `&'static dyn Device`，按名字查出来后用
  `as_stream/as_block/as_control/as_bus/as_event` 向下转型取能力。
- 新增能力 = 新增一个 trait + 新增一个 `as_xxx` 默认方法，注册表本体不动。

### 3.3 四个能力 trait

#### 字节流设备 `StreamDevice`

对齐生态 `Read/Write` 的形状；因注册表返回的是共享 `&'static dyn`，
本内核使用 `&self` + 内部可变性，而不是 `&mut self`。

```rust
/// 字节流设备（对齐 embedded_io::Read / Write 的语义）
pub trait StreamDevice: Device {
    /// 接收缓冲中当前可读字节数（非阻塞探测）
    fn available(&self) -> usize;

    /// 非阻塞读：最多读 buf.len()，返回实际字节数；无数据返回 Ok(0)
    fn read(&self, buf: &mut [u8]) -> Result<usize, DeviceError>;

    /// 写：可短暂阻塞等待流控（等 TXE / FIFO 空），返回实际写入数；非空缓冲通常写满
    fn write(&self, buf: &[u8]) -> Result<usize, DeviceError>;

    /// 写满整个缓冲区；防御性检查：连续写 0 字节报 WriteZero
    fn write_all(&self, buf: &[u8]) -> Result<(), DeviceError> {
        // 默认实现：循环调用 write，直到写完
    }
}
```

- `available()` 就是原 `rx_len()`，但名字更通用，语义是“可读性探测”。
- `read` 为非阻塞（无数据 Ok(0)）；`write` 为短暂阻塞等待流控（真实 UART 的 TXE/FIFO 语义）。
  非阻塞读与 `embedded_io::Read` 对齐，便于后续桥接。
- 阻塞读不放进 trait 基础能力，而由内核提供的通用适配器实现（见第 8 节设计决策）。

#### 块设备 `BlockDevice`

```rust
/// 块设备：文件系统只需要“读扇区 / 写扇区”两个原语
pub trait BlockDevice: Device {
    /// 逻辑扇区大小（字节）
    fn sector_size(&self) -> u64;

    /// 设备总扇区数
    fn sector_count(&self) -> u64;

    /// 读一个扇区到 buf；buf.len() 必须等于扇区大小
    fn read_sector(&self, no: u64, buf: &mut [u8]) -> Result<(), DeviceError>;

    /// 写一个扇区；buf.len() 必须等于扇区大小
    fn write_sector(&self, no: u64, buf: &[u8]) -> Result<(), DeviceError>;
}
```

块设备不使用 `Read/Write`，因为块设备寻址单位是扇区，不是字节流。

#### 控制面 `Control`

```rust
/// 控制面：ioctl 风格，任意设备都可实现
pub trait Control: Device {
    /// 执行控制指令；op 语义由设备自定。arg 为输入/输出字节缓冲，返回 Ok(实际写回字节数)。纯标量操作约定 arg 为 4 字节 LE 槽或空缓冲。
    fn control(&self, op: u32, arg: &mut [u8]) -> Result<usize, DeviceError>;
}
```

- 用于波特率配置、读清错误状态、LED 开关、厂商私有命令等。
- 一个设备可以同时是 `StreamDevice` 且实现 `Control`（例如 UART 的
  波特率配置），也可以只是 `Control`（例如 LED）。

#### 总线设备 `BusDevice`

```rust
/// 总线传输能力（SPI 全双工）
pub trait BusDevice: Device {
    /// 一次传输：发送 tx，同时把读入字节写入 rx。
    /// rx 为空表示只写；tx 为空表示只读（具体时序由总线驱动决定）。
    fn transfer(&self, tx: &[u8], rx: &mut [u8]) -> Result<(), DeviceError>;
}
```

- `BusDevice` 只表达 SPI 全双工事务；片选 / 时钟相位 / 极性由具体驱动内部持有。
- I2C / I3C 的“从机地址是事务参数”，与本签名不相容；待有真实 I2C 器件接入时另立带地址的 `I2cDevice`，不并入 `BusDevice`。
#### 事件 / 唤醒设备 `EventDevice`

```rust
/// 可等待事件设备：为阻塞 I/O 提供 ISR 唤醒通道
pub trait EventDevice: Device {
    /// 注册一个等待者（通常为任务指针）；数据/状态就绪时由设备负责唤醒
    fn register_waiter(&self, waiter: usize) -> Result<(), DeviceError>;
    /// 立即唤醒当前等待者
    fn wake(&self);
}
```

- UART 的 waiter 槽 + ISR 唤醒就是现成实现；
- 内核提供通用阻塞适配器：`read_blocking(&dyn StreamDevice, &dyn EventDevice, buf)`
  —— `available()==0` 时 `register_waiter` + `block()`，唤醒后重试；
- 按名消费者可经 `find_stream + find_event` 组合出阻塞读，不退化到轮询。

## 3.4 错误模型

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum DeviceError {
    Duplicate,       // 注册时名字重复
    Full,            // 注册表满
    InvalidInput,    // 参数非法（扇区越界 / seek 越界）
    Unsupported,     // 控制命令 / 能力不被支持
    Io,              // 底层 IO 错误
    Timeout,         // 操作超时
    UnexpectedEof,   // 读到卷尾（fatfs::io::IoError::new_unexpected_eof_error 的对应物）
    WriteZero,       // write_all 防御性停滞（fatfs::io::IoError::new_write_zero_error 的对应物）
}
```

## 3.5 能力不是封闭的：从核心能力到“能力矩阵”

**能否覆盖所有设备？** 仅靠核心四个能力也不够；但本设计的关键
不是“四类”，而是 **`Device` 顶层 + 开放的能力 trait 集合 + `DeviceKind` 分类**。
新增设备类不改注册表，只加一个 trait 和（可选的）`DeviceKind` 变体。

| 设备 | 主要能力 | 备注 |
|---|---|---|
| 串口 UART / CDC 串口 | `StreamDevice` + `Control` | 最典型的字节流 |
| 网卡 / WiFi | `NetDevice` + `Control` | 帧收发；扫描/连接走 `Control` |
| LED | `Control`（或 `Gpio`/`Pwm`） | 纯控制设备；亮度/呼吸灯走 PWM |
| Flash（NOR/NAND） | `BlockDevice` + `Control` | 擦除/写保护等走 `Control` |
| USB MSC（U 盘） | `BlockDevice` | 类驱动之下暴露成块设备 |
| USB HID（键鼠） | `HidDevice` + `Control` | 报告描述符/输入报告 |
| USB 摄像头 | `FrameDevice` + `Control` | 帧流 + 格式协商 |
| LCD / Display | `DisplayDevice` + `Control` | framebuffer / 开窗写点，不是字节流 |
| BLE | 传输层 `StreamDevice` + `Control` | GATT/协议层在设备之上，不压进叶子 trait |
| 摄像头 | `FrameDevice` + `Control` | 设格式 → 排队缓冲 → 取帧 |
| 麦克风 / 喇叭 | `StreamDevice`（PCM）+ `Control` | 采样率/通道/位深是控制参数 |
| SPI 总线 | `BusDevice` + 上层具体设备 | 全双工；I2C / I3C 待接入时另立带地址 trait |
| ADC（模数转换） | `StreamDevice`（采样流）+ `Control` | 通道 / 采样率 / 分辨率；单次或连续采样 |
| DAC（数模转换） | `StreamDevice`（采样流）+ `Control` | 通道 / 输出电平 / 波形生成 |

对应扩展能力 trait（示意，均继承 `Device`）：

- `NetDevice`：帧收发、套接字语义。
- `DisplayDevice`：framebuffer / 窗口 / 刷新。
- （音频 PCM：`StreamDevice` + `Control`，不单独设 `AudioDevice`）
- `FrameDevice`：摄像头帧缓冲 / 格式 / 采集。
- `GpioDevice` / `PwmDevice`：引脚电平与占空比。
- `CanDevice`：CAN 帧收发。
- （SPI 全双工由核心 `BusDevice` 表达；I2C / I3C 待接入时另立带地址 trait，不并入）
- （ADC / DAC：`StreamDevice` + `Control`，不单独设 `AdcDevice` / `DacDevice`）


原则：

1. 叶子驱动层只表达“这个设备能干什么”，协议栈/类驱动放在设备之上或之下。
2. 复合设备（USB / WiFi / BLE / 摄像头）天然是“控制器 + 类驱动 + 协议栈”的
   分层结构；它可能同时暴露多个能力（例如 USB 摄像头暴露 `FrameDevice` 与
   `Control`），而不是被硬塞进某一个类。
3. 注册表永远只认识 `Device`，能力扩展对它透明。

## 3.6 哪些能收敛到 Stream/Block，哪些必须专属 trait

判定规则：

- 数据面是**连续字节流、边界由上层协议管理** → `StreamDevice` + `Control`。
- 数据面是**随机访问的定长块** → `BlockDevice` + `Control`。
- 数据面有**强语义边界**（帧 / 报告 / 采样格式 / 像素窗口）→ 才需要专属 trait。

| 设备 | 能否收敛 | 说明 |
|---|---|---|
| 串口 / BLE 传输层 | 能 | `StreamDevice` + `Control` |
| 音频 PCM（麦克风 / 喇叭） | 能 | 采样即字节流，格式/速率走 `Control` |
| ADC / DAC 采样流 | 能 | 采样值序列 = 字节流，通道/分辨率走 `Control` |
| 摄像头（MJPEG 等压缩流） | 能 | 压缩视频是字节流 |
| Flash / SD / eMMC | 能 | `BlockDevice` + `Control` |
| SPI 器件 | 用 `BusDevice` | 全双工事务；I2C 器件待接入时另立 trait |
| 网卡 / WiFi | 不建议硬塞 | 帧 + 链路状态 + 时间戳，不是无边界字节流 |
| HID（键鼠） | 不建议硬塞 | “报告”有边界 |
| 摄像头（原始帧） | 建议专属 | 格式协商 + 帧缓冲队列 → `FrameDevice` |
| LCD | 建议专属 | framebuffer 随机写 + 窗口/刷新 → `DisplayDevice` |

结论：**当前书的核心是 `Device` + `StreamDevice / BlockDevice / Control / BusDevice`
四个能力 trait**；音频 / ADC / DAC 用 `StreamDevice + Control` 表达；
`NetDevice / DisplayDevice / CanDevice / GpioDevice / PwmDevice / FrameDevice / HidDevice / TimerDevice / RtcDevice / WdgDevice / DmaDevice` 等按需扩展；音频 / ADC / DAC 用 `StreamDevice + Control` 表达。
## 3.7 总线审计：UART / SPI / I2C / I3C / I2S / RS-485 / CAN

这些都是**总线 / 物理层**，但“总线”不等于同一个数据面形态。分层判定：

| 总线 | 数据面形态 | 驱动抽象 |
|---|---|---|
| UART | 字节流 | `StreamDevice` + `Control`（波特率 / 校验 / 流控） |
| RS-485 | 字节流 + 方向控制 | `StreamDevice` + `Control`（DE/RE 方向引脚） |
| I2S | PCM 字节流 | `StreamDevice` + `Control`（采样率 / 位深 / 声道） |
| SPI | 同步字节事务 | `BusDevice::transfer` + `Control`（时钟相位 / 极性 / 片选） |
| I2C / I3C | 地址化字节事务 | 待接入时另立带地址 `I2cDevice`；不并入 `BusDevice` |
| CAN | 报文帧 | `CanDevice` + `Control`（波特率 / 接收过滤） |

结论：

- `StreamDevice` 不只代表“串口”，而是代表**“字节流”这一数据面形态**；
  UART / RS-485 / I2S 都是总线，但它们对软件暴露的是字节流，所以走 `StreamDevice`。
- `BusDevice` 代表 **SPI 式全双工同步事务**；I2C / I3C 带地址语义，待接入时另立 trait。
- CAN 是**“报文帧”数据面**，不能压成字节流或字节事务，需要专属 `CanDevice`。
- `BlockDevice` 是存储类能力，不是总线；例如 SD 卡走 SPI 时，是“SPI 总线上的一个块设备”。
## 3.8 其他控制器：PWM / GPIO / Timer / RTC / Watchdog / DMA

嵌入式里远不止串口、存储和网络，还有大量控制器。它们遵循同一条扩展原则：
**新增一个控制器 = 新增一个能力 trait +（可选）一个 `DeviceKind` 变体，注册表不变。**

| 控制器 | 数据 / 控制形态 | 抽象 |
|---|---|---|
| PWM | 周期 + 占空比 | `PwmDevice` + `Control` |
| GPIO | 方向 + 电平 | `GpioDevice` + `Control` |
| Timer | 定时 / 比较 / 捕获 | `TimerDevice` + `Control` |
| RTC | 时间读写 | `RtcDevice` + `Control` |
| Watchdog | 使能 / 喂狗 | `WdgDevice` + `Control` |
| DMA | 内存搬运 | `DmaDevice` + `Control` |

原则一句话：**不试图用一个固定枚举装下所有控制器**，而是
`Device + DeviceKind + 开放能力 trait`；每类控制器各有一个语义匹配的 trait，
用到哪类就加哪类，注册表保持透明。
## 3.9 与 embedded Rust 生态 HAL 的关系

- `embedded-hal` / `embedded-io` / `embedded-storage` 等是**芯片外设 / 寄存器级**的底层 trait；
  我们在驱动**实现内部**按需复用或桥接它们，但**不作为设备管理层的对外主抽象**。
- 对外暴露的是**我们自己设计、贴合内核使用习惯**的能力 trait：核心四能力 + 按需扩展
  （`NetDevice` / `DisplayDevice` / `CanDevice` / `GpioDevice` / `PwmDevice` / `HidDevice` /
  `FrameDevice` / `TimerDevice` / `RtcDevice` / `WdgDevice` / `DmaDevice`）。
- 这样做的原因：生态 trait 面向“跨芯片通用”，方法签名 / 错误类型 / 组合方式并不总是符合
  本内核“对象安全、统一 `DeviceError`、共享 `&self`、按名分发”的要求；与其被生态 API 牵着走，
  不如自持一套稳定、舒适的教学抽象，实现时再按需适配到生态 trait。
- 真正要守住的边界：**不重写寄存器级代码**——HAL 仍由芯片 HAL crate 提供；我们只做
  “设备对象化 + 能力 trait + 注册表”。
## 3.10 设计取舍：这是要上战场的系统，不是玩具

设备抽象层是系统的“承重墙”。它被任务、中断、文件系统、网络栈、应用同时依赖，
一旦接口漂移或语义含糊，代价会扩散到全系统。因此取舍排序是：

1. 正确性 / 实时性
2. 可维护性 / 可审计性
3. 扩展性
4. 与生态 API 的一致性（最末）

### 为什么不是直接拿 embedded-hal / embedded-io 当主抽象

| 维度 | embedded-hal / embedded-io 的形态 | 生产系统需要 | 我们的取舍 |
|---|---|---|---|
| 类型擦除 | trait 多带 `type Error`、泛型参数、`&mut self` | 能存进 `&'static dyn Device`、按名查、跨任务/ISR 共享 | 固定 `DeviceError`、`&self`、`as_*` 能力下转型 |
| 错误模型 | 每个驱动自定 Error，错误类型蔓延 | 上层（fs/net/应用）统一处理 I/O/控制错误 | 全局统一 `DeviceError` |
| 生命周期 | 没有设备生命周期约定 | 明确“谁拥有设备、谁持有引用、何时 init、何时 find” | `'static` 实例 + 注册表只登记不拥有 |
| 并发/中断 | 不定义同步模型 | 明确 ISR/任务边界、临界区、单写多读契约 | 所有表访问在 `sync::free`；设备内部自持可变状态 |
| 按名绑定 | 没有注册表/查找 | 生产者与消费者解耦、静态设备表 | `DriverRegistry` + `DeviceTable` |
| 通用控制面 | 故意不定义 ioctl | 波特率、厂商命令、错误清读等必须有出口 | `Control` |

结论：**生态 trait 负责“寄存器级的事实”，我们负责“系统级的契约”。**
生态 API 不是不能用，而是它解决的问题和我们这层要解决的问题不在同一个层次。

### 具体理由

1. **对象安全是硬约束。**
   注册表必须能存异构设备（`&'static dyn Device`），并在运行期按能力分发。
   `embedded-io` 的 `type Error` 和 `&mut self` 使 trait 对象无法稳定、安全地挂进定长表；
   我们以固定错误类型 + `&self` + 内部可变性换取“一张表装下所有设备”。

2. **统一错误让上层代码可写、可审。**
   如果每个驱动各带一个 Error 类型，文件系统/网络栈/应用就得为每个设备泛型展开，
   或者吞错。生产系统宁可少一些类型灵活，也要一致、可穷尽的错误分类。

3. **实时纪律必须显式。**
   单核关中断模型下，“谁在 ISR 写、谁在任务读、哪里取锁”不能靠惯例，必须写进类型和文档。
   我们的 `&self` + `sync::free` + 设备内部 SPSC/RefCell 契约，正是把并发风险关进笼子。

4. **无动态分配、无碎片。**
   编译期清单 + 定长注册表 + `Box::leak`/静态实例，运行期没有分配器介入设备管理，
   这对长期运行和可预测性是决定性的。

5. **核心稳定、外设扩展不破坏核心。**
   新控制器 = 新 trait + 可选 `DeviceKind` 变体 + `as_xxx`；注册表和既有驱动不用动。
   这是给长期演进的“结构稳定性”。

6. **控制面不可省。**
   真实外设几乎没有不需要配置/查询/私有命令的；`Control` 是生产驱动的事实接口。

### 边界（哪些仍交给生态）

- 寄存器读写、时钟、引脚、DMA 等**芯片级实现**继续由芯片 HAL/PAC crate 提供。
- 我们在驱动实现内部**可以**把生态 trait 作为桥接，但**不**把它当作设备层对外的公共契约。
## 4. 注册与查找

### 4.1 运行期注册表 `DriverRegistry`

```rust
pub const DEV_CAP: usize = 8;

pub struct DriverRegistry {
    devices: RefCell<[Option<(&'static str, &'static dyn Device)>; DEV_CAP]>,
}

impl DriverRegistry {
    pub const fn new() -> Self;
    pub fn register(&self, name: &'static str, dev: &'static dyn Device)
        -> Result<(), DeviceError>;
    pub fn find(&self, name: &str) -> Option<&'static dyn Device>;
    pub fn unregister(&self, name: &str) -> bool;

    pub fn find_stream(&self, name: &str) -> Option<&'static dyn StreamDevice>;
    pub fn find_block(&self, name: &str) -> Option<&'static dyn BlockDevice>;
    pub fn find_control(&self, name: &str) -> Option<&'static dyn Control>;
    pub fn find_bus(&self, name: &str) -> Option<&'static dyn BusDevice>;
}
```

- 名字全局唯一，跨类同名算 `Duplicate`。
- 注册表不拥有设备；设备由创建方 `Box::leak` 或静态存储保证 `'static`。
- 所有访问都发生在 `sync::free` 临界区内。

### 4.2 编译期清单 `DeviceTable`

```rust
pub struct DeviceSlot(UnsafeCell<Option<&'static dyn Device>>);
pub struct DeviceDef {
    pub name: &'static str,
    slot: &'static DeviceSlot,
}
pub struct DeviceTable(UnsafeCell<Option<&'static [DeviceDef]>>);

macro_rules! device_list { /* 声明 const 清单 */ }
```

语义与旧 `drv_static` 一致：名字/集合在编译期定形，实例在 init 里
`fill` 一次；槽未填 = 未就绪，`find` 返回 `None`。`DeviceTable` 同样提供 `find_stream/find_block/find_control/find_bus`。

## 6. 生命周期与并发纪律

- 设备实例 `Box::leak` 或放静态存储，句柄为 `&'static dyn Device`。
- trait 方法一律 `&self`，可变状态由设备内部用 `RefCell` / `AtomicUsize` /
  `UnsafeCell` 自持，与内核 `Queue`/`Notifier` 同款。
- 注册表 / 清单内部状态全部在 `sync::free` 临界区内访问；
  `unsafe impl Send/Sync` 的理由与 `bus.rs` 同构。
- 所有能力 trait 经 `Device: Sync` 上界保证 `dyn Device` 及能力 trait 对象可 `Send`；`DrvLed`（RefCell）等设备需补 `unsafe impl Sync` 并给出 SAFETY 论证。

## 7. 与现有实现的差异 / 迁移映射

| 旧 | 新 |
|---|---|
| `DeviceApi::Led` | `DeviceKind::Control` + `Control` |
| `LedDevice::{on,off,toggle}` | `Control::control(op=LED_ON/OFF/TOGGLE)` |
| `DeviceApi::Uart` | `DeviceKind::Stream` + `StreamDevice` |
| `UartDevice::rx_len` | `StreamDevice::available` |
| `UartDevice::read_byte` | 内核通用阻塞适配器（`StreamDevice + EventDevice`，见第 8 节） |
| `UartDevice::write_all` | `StreamDevice::write_all` |
| `DeviceApi::Bd` | `DeviceKind::Block` + `BlockDevice` |
| `BdError` | `DeviceError` |
| `register_led/register_uart/register_bd` | `register(name, &dyn Device)` + `find_xxx` |

## 8. 设计决策（已定）

1. **`StreamDevice::read` 为非阻塞**（无数据 Ok(0)）；**`write` 为短暂阻塞等待流控**（等 TXE/FIFO）；保留 `available()` 做可读探测。
   阻塞读（“等待即 Blocked”）由内核提供的通用适配器实现，不进 trait 基础能力。
2. **LED 这类纯控制设备走 `Control`**：`on/off/toggle` 编码为三个 `op`；
   后续需要 PWM 亮度时再加 `PwmDevice`，不改 `Control`。
3. **保留 `DeviceError::Unsupported`**：控制命令/能力不被支持时返回错误，不 panic。
4. **不把阻塞 `read_byte` 放进 `StreamDevice` 默认方法**；阻塞读由内核提供的通用适配器实现：
   `read_blocking(&dyn StreamDevice, &dyn EventDevice, buf)`，按名消费者用 `find_stream + find_event` 组合得到。
