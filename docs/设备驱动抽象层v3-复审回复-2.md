## 1. P1（必须改）§5.15.1 的 owner 覆盖不到本仓的 12 个句柄

### 证据

```sh
# 设备层不碰 hal 总线（只有 doctest 断言 Sync）
grep -rn -e 'hal::i2c' -e 'hal::spi' -e 'hal::gpio' src/device
# → 仅 src/device/mod.rs:133-135 的 doctest

# 12 个句柄全部转发到厂商 SDK
grep -n 'os_dev_ic_open\|os_dev_scan_' src/device/pal/quectel.rs
# → 34/35 …，经 *_abi.rs 的 extern "C" → cris_*/ql_*

# 总线 actor 零调用方（Phase-0 占位）
grep -rn 'device::Bus\|Bus::new()' src crates firmware | grep -v 'src/device/bus.rs'
# → 只有 src/device/mod.rs:48 的 doctest
```

结论：本仓 12 个句柄的方法**不经过 `BusDevice::transfer`**，也就**不经过
`BusArbiter::with_transaction`**。§5.15.1「调用者即 owner」对它们不成立；§9 第 5 条
（`:844-845`）与 §10.1 第 2 条（`:879`）写「归属表已下沉、不再是待定项」——对本仓不成立。

### 处置（二选一，推荐 A）

**A（推荐）**：§5.15.1 增一段「厂商 SDK 设备」：

```text
厂商 SDK 设备（不经 BusDevice、总线由厂商库内部持有）：
- owner 由 handle 的 `const OWNER: &'static str` 声明（可与 MODEL/CLAIMS 合并成一张设备表）；
- core 提供 claim 守卫：`claim_owner(dev, task) -> Result<OwnerGuard, DeviceError>`
  （同一设备第二次 claim → Busy，OwnerGuard Drop 释放）；
- dev/host 构建下所有 C2 入口 `debug_assert_eq!(owner_of(NAME), Some(current_task()))`
  （复用 R8 的断言机制；release 编译期剔除，零开销）；
- `with_transaction` 只覆盖经自有总线的设备（本仓目前为 0 个，等 ToF/camera 驱动落地）。
```

验收（机器可判，host 两条用例）：
1. 同一设备两次 `claim_owner` → 第二次 `Err(Busy)`；
2. 非 owner 任务调用 C2 方法 → dev 构建断言触发。

**B**：不改规范，§5.15.1 与 §9-5 明确写「厂商 SDK 设备不在 `with_transaction` 体系内，
R3 对其**不可判、靠约定**」；样本项目自行加守卫。§9-5 的「已下沉」改为「**部分下沉**」。

> 无论 A/B，**不能保留现状的表述**：它会让读者以为 R3 已有执行机制。
> 设计权衡 §3.1 把它列为"唯一会导致运行期数据竞争"的项，这一条必须落到纸上。

### 需要改的位置

- §4.7 R3（`:169`）：补一句「厂商 SDK 设备的 owner 见 §5.15.1」；
- §5.15.1（`:667`）：补「厂商 SDK 设备」段；

- §10.1 第 2 条（`:879`）：同上措辞。

## 2. P1b `EventChannel<T, N>` **不能**别名 `Receiver<T>`

### 证据

| | 本仓 `Receiver<T>` | v3 `EventChannel<T, N>` |
|---|---|---|
| 表示 | `Arc<ChannelInner<T>>`（`mpsc.rs:480`） | `[MaybeUninit<T>; N]` 内联 |
| 容量 | 运行期 `channel(cap)`（`mpsc.rs:270`） | 编译期常量 `N` |
| 分配 | 堆 | 零分配 `const fn new()` |
| 泛型元数 | `T` | `T, N` |

消费面不是 2 处：`Receiver<` 在设备层与平台层出现 **25 处 / 10 个文件**
（`device/{pinpad,mod,bus}.rs`、四个 PAL 后端、`service/{display,cellular}.rs` 等）。

### 处置

- §10.3 行 4（`:901`）与 §10.4 第 4 条（`:925`）：「实现/别名」→
  「**新增 `EventChannel<T, N>` 并逐设备迁移事件消费点（25 处 / 10 文件）**」；
- 明确分工：`sync::mpsc` 保留给非设备用途（服务/线程间）；设备事件一律走 `EventChannel`；
- 计入 §10.6 **第二段**（不是第一段的"别名"级工作量）。

### 附带发现（同一处矛盾）

§8.3（`:818`）写「容量统一用 8；**禁止**每个设备自定义 N」，§10.4-4（`:925`）写
「`EventChannel<T, 8>`（**容量按设备调整**）」。二选一：
- 若要按设备调整：§8.3 改成「默认 8；确需调整须在设备文档写明理由，并在反膨胀表里登记
  `(T, N)` 组合数」；
- 若要统一 8：删掉 §10.4-4 的括注。

## 3. P2 §8.3 的 flash 预算不可外推

表测的是 `thumbv7m`（Cortex-M3）、6 设备 × 3 方法 × 2 调用点。本仓目标是 armv7-a / armv7-r，
面是 13 句柄 / ~200 契约方法。据此：

- 「整个 v3 能力面 + core 层 ≈ 1.7 KB」只对那 18 个方法成立，**不能当样本项目的预算承诺**；
- vtable 随（类型 × trait × 方法）线性增长，200 方法面必须重测。

处置：表头加一行「**微基准：thumbv7m、18 个方法；不代表样本项目**」，并把
「限制存储的不是这层抽象，是图形与协议栈」保留为定性判断（这条我认同）。

## 4. P3 两处小不自洽

1. §6 矩阵（`:715`）把打印机映射成 `StreamDevice + Printer`，但本仓打印机的厂商面是
   `Print_Line`/`Print_Barcode`/`Print_DotMatrix`，**没有裸字节通路**，`StreamDevice::read/write`
   无处落地。→ 删掉 `StreamDevice`，或标注「待厂商提供裸字节通道」。
2. §6 是"非规范"矩阵，却引用附录·非规范的 §5.12 `FrameSink`。→ 注明「见 §5.12（附录）」。
