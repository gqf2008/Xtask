# 设备驱动抽象层 v3 · 设计权衡（过度设计 / 设计不足）

> **本文件不是规范**。规范是 `docs/设备驱动抽象层v3.md`，冲突时以它为准。
> 本文记录 2026-10-29 的第三方审查结论：哪些地方设计过度、哪些地方设计不足，
> 以及据此做过的改动。**本文是"决策记录"，不是"第二份规范"**——它存在的目的正是
> 把规范正文里的自我论证、历史修订、评审对话搬出来，让正文只描述"现在是什么"。

## 0. 判定方法

对照 Linux 的做法只看五件事，不看"像不像 Linux"：

| 判据 | Linux 的对应物 | 问的问题 |
|---|---|---|
| 谁的 core 拥有状态 | driver core、`i2c_adapter`、`regmap` | 仲裁/生命周期/背压有没有归属，还是靠约定 |
| provider / consumer 是否分离 | `gpiod_get`、`regulator_get`、pinctrl | 驱动只提供 ops，取用侧是否走框架 API |
| 背压语义 | V4L2 buffer queue、TTY `tty_buffer`、`evdev` client buffer | 队列满时返回什么、谁被丢、ISR 是否可用 |
| 失败路径 | probe 回滚、`remove` 顺序、runtime PM resume 顺序 | 半初始化怎么撤销、reset 期间在途请求怎么办 |
| 规则可判性 | `might_sleep()`、lockdep、`CONFIG_DEBUG_ATOMIC_SLEEP` | 纪律是断言还是文档 |

以及一条元判据：**规范只写"现在是什么"，历史与辩护放附录**（Linux 的做法是 commit message + `Documentation/process/`）。

## 1. 结论摘要

- **形状层面已经和 Linux 同构，不需要再动**：能力类型化、总线两层、上下文三级、保留 `ioctl_raw` 逃生舱、`DeviceBase`/`Device` 拆分。
- **过度设计集中在"对称性、分类学、自我辩护"**：§5.12/§5.14 的 9 个零实现预留面（约 124 行）、§5.4「四条全中才叫 Transaction」这类不可判断言、散落在 §5.1/§5.4/§8/§10 的重复论证。
- **设计不足集中在"框架层与失败路径"**：没有 core 层定位（仲裁靠口头约定）、`post` 满时语义未定义、open 失败回滚未规定、初始化顺序隐式、缺 `regmap` 形状的寄存器访问助手。
- 还有一处**规则很重、执行面为零**的错配：C0/C1/C2 与 R1–R7 靠评审维护，而 Linux 用运行时断言。
- **范围修正（2026-10-30，L2）**：§3.1/§3.5 的“补 core 层/RegMap/仲裁”不再进内核，
  留给产品层——见 §9。内核只做“把设备接进调度器”。

## 2. 过度设计（含处置）

### 2.1 零实现的预留面占了 16%

§5.12（`FrameSource`/`FrameSink`/`SampleSource`/`SampleSink`/`TextSink`）+ §5.14
（`PowerManaged`/`AsyncOp`/`DmaBuffer`/`Recoverable`）= 9 个 trait，本仓实现数 0。

V4L2/ALSA/IIO 值几百页规范，是因为背后有成千上万驱动和一个冻结的用户态 ABI；本仓两者都没有。
"对称好看"不构成理由，而**代价是真实的**：每多一个面，就要在 §5.5 分类骨架、§6 矩阵、§8 验收各对齐一次
（本轮就因 `SampleSource` 与 ADC 的分类错误开过一条缺陷）。

**处置**：§5.12、§5.14 标题标注「附录·非规范」；规范项只保留三个——
`DmaBuffer`（DMA 对齐/所有权是安全属性）、`Recoverable`（`reset` 与 owner 队列的交互现在就要定）、
`FrameSink`（`Display` 的真实像素面）。`AsyncOp` 可删：`PollingAsyncOp` + `EventChannel` 已覆盖，
`Future` 包装在应用层 30 行即可。

### 2.2 元论述混进规范条款

证据：§5.1「移植方义务……样本项目 13/13」、§5.4 前言「在卡/PIN 类产品里它是核心形态，但并非唯一形态」、
§8「对齐修订 2026-10-29，三轮定稿」、§10.1「基准教训（存档）」。

同一段论证在 §5.1/§5.2/§5.9/§10 各出现一次 → **改一处漏三处**。

**处置**：本次已把新结论写进本文（决策记录），规范正文只留一行指针；
后续可把旧论证逐步搬到本文，删正文中的"第几轮定稿"字样。

### 2.3 `Transaction / Session` 的四条判定是分类学，不是接口

原文「四条全中才叫 Transaction，缺一条就说明它其实是别的东西」——Linux 从不定义"什么算 Transaction"，
且「独占到什么程度算独占」不可判。

**处置**：降级为描述性特征清单（用于归类与自查），删除"缺一条就说明"的规范断言。

### 2.4 `EventChannel` + `Broadcast` + `EventDevice` 三件套偏重

Linux 也有三件套（`poll`/`wait_queue`、`kfifo`、`evdev` 多 client buffer），所以分层方向对；
过度的是**本仓没有多消费者的真实压力**（键盘 UI+业务 = 2 个消费者，可在应用层汇合）。

**处置**：不砍 `Broadcast`，但标记「按需实现、不阻塞 §8」；先允许键盘退回
「单 `EventChannel` + 应用层汇合」验证需求，再决定是否下沉为设备能力。

## 3. 设计不足（含处置）

### 3.1 【最重要】没有 core 层的定位 → 新增 §5.15

Linux 的核心抽象不是"设备能力 trait"，而是 **provider/consumer 分离 + core 拥有状态机**
（`i2c_adapter` 的锁 + `i2c_client` 生命周期；`regmap` 的读写助手；driver core 的三元组）。

原文档的层次是"规范 + 驱动 + 应用"，中间那层缺失，后果：

- 「共享总线由 owner 串行化」——但 **owner 是谁**？答案原本是 §9 待定的"设备归属表"，
  等于把最关键的调度问题留给约定；
- 一个 I2C 上挂 5 个器件时，`transfer` 的事务原子性无可实现机制；
- R3 的可判性同样依赖归属表，形成同一空洞。

**处置**：新增 §5.15「core 层（框架层）职责」：三职责（仲裁 / 生命周期与注册 / consumer API）
+ `BusArbiter::with_transaction`（持同一物理总线的零分配共享锁，release 生效）+ `RegMap`；
自有总线设备的 **owner = `with_transaction` 调用点**；
**厂商 SDK 设备**（不经 `BusDevice`）用 `OWNER` 声明 + `claim_owner` 守卫（§5.15.1），
两类并列；归属表降级为诊断输出（§9 第 5 条同步改写）。

这是全部不足中唯一会导致**运行期数据竞争**的一条。

### 3.2 失败路径与回滚没有规范 → §5.6 新增「失败路径」

原 §5.6 只有「close 幂等、析构不能返回错误、未 open 返回 `InvalidInput`」，缺 probe 回滚、
`reset` 与 owner 队列的交互、半初始化状态。POS 设备的真实故障源（USB 拔插、卡座抖动、屏初始化超时）
全落在这一段。

**处置**：`open` 失败必须回到"完全未 open"且可重试；`reset` 期间在途命令丢弃回 `Cancelled`；
`Drop` 顺序（停 owner → close → 释放缓冲）。

### 3.3 `post` 满时语义未定义 → §5.8 新增「满时语义」

`post(&self, v: T) -> Result<(), DeviceError>` 没说环满返回什么（`Full`？丢最旧？计数？），
而 §10.3 第 11 行说载荷走"槽池"——槽池本身又不在规范里，背压因此悬空。

Linux 每个子系统都必须回答（V4L2 丢帧策略、TTY buffer 上限、evdev 溢出同步）。

**处置**：环满一律 `Err(Full)`、**不覆盖已入队事件**；ISR 侧不重试不记日志（改由容量设计保证），
`overflow_count()` 暴露给诊断与单测。

### 3.4 没有初始化顺序 → §5.13 新增「初始化顺序」

三种绑定形态只解决"名字 → 实例"，不解决顺序。POS 设备是"电源 → 总线 → 器件"三段式，
当前靠 `examples/led.rs` 的手写顺序，`init()` 里是隐式保证。

**处置**：静态顺序 = 清单顺序；依赖失败立即 panic 并打出依赖名；**不引入延迟 probe**
（本仓无模块加载，`EPROBE_DEFER` 的复杂度没有对应收益）。

### 3.5 缺 `RegMap` 形状的寄存器访问助手 → §5.15.2

§5.3 只有裸 `BusDevice::transfer`，每个 I2C 器件驱动都要自己拼 `tx/rx`、处理"先写地址再读"的两段事务、
16 位地址宽度与字节序。Linux 上这类代码 90% 被 `regmap` 消掉。

**处置**：`RegMap::read/write/update_bits/poll_bits`（`update_bits` 的读-改-写必须在同一个
`with_transaction` 内；`poll_bits` 走 `Duration`，遵守 R7）。纯函数级抽象，无设计争议，收益立即可见。

## 4. 规则很重、执行面为零（错配）

R1–R7 是全篇最严条款，但 R3 自己承认需要"设备归属表"才能可判，而 C 级标注靠"每个方法必须声明" +
评审维护。Linux 的对应物 `might_sleep()`/lockdep 都是**运行时断言**——只靠纪律一定会腐化。

**处置**：新增 **R8**：core 层提供 `in_critical_section()`，所有 C2 方法入口
`debug_assert!(!in_critical_section())`；C0 方法不得接受 `&mut self`、不得返回带生命周期的借用。
§8 验收从"grep 文本"升级为"跑测试"。

## 5. 与 Linux 同构、不应再动的部分

1. **保留 `ioctl_raw` 逃生舱是对的，比 v2 的"消灭万能控制面"更现实。** Linux 从没消灭 `ioctl`，
   它做的是**分层收敛**：规则命令抽成类型化子系统，真正不规则的留 `ioctl`。v3 §5.10 正好是这个形状；
   但**保持每设备形状、不做全局能力**——完整权衡见 §5.1。
2. **总线两层（`transfer` + 族 typed trait）与 Linux 的 `i2c_transfer`/`spi_transfer` + 子系统专属命令同构。**
   §5.9 里"不做全局 `BusCmd`"的反例论证要保留——它是**不许回退的护栏**。
3. **上下文三级方向对**（只是要配 R8 的断言）。
4. **`DeviceBase`/`Device` 拆分方向对**（Linux 亦有 `struct device` 与 ops 表不要求 `Sync` 的分离），
   只是 v3 §5.1 不必自带四段辩护。

### 5.1 逃生舱的形状：每设备 `IoCtl`，不是全局 `RawControl`

问题：v2 曾设计 `RawControl: Device { unsafe fn control_raw(op: u16, arg: *mut c_void) }` +
`as_raw_control()`，让任何 `&dyn Device` 都能转入原始控制通道。v3 改为
`IoCtl: DeviceBase { unsafe fn ioctl_raw(&self, op: u32, arg: *mut c_void) -> Result<isize, DeviceError> }`，
**不经 `as_*`**，由持有具体设备（typed accessor）的调用方直接使用。

| 备选 | 形状 | 裁决 |
|---|---|---|
| A | `RawControl: Device` + `as_raw_control()` | 否决：`Device: Sync`，而真实用到逃生舱的 7 个设备是 `Send + !Sync` 独占句柄，实现不了。要救它只能去掉 `Device` 的 `Sync`，连带废掉注册表/`as_*` 的共享前提 |
| B | `RawControl: DeviceBase` + `as_raw_control()` | 否决：解了 `Sync` 冲突，但保留"统一发现"——任何 `&dyn Device` 都能拿到发任意 op 的通道，v1 `Control(op, arg)` 的病根（弱路径永远可达）原地复活 |
| C（采纳） | 每设备 `IoCtl: DeviceBase`，不经 `as_*` | 贴合真实形状（7 个设备各自声明 `ioctl_raw`）；逃生舱存在但不可被统一发现；op 契约留在设备族文档 |
| D | 不做逃生舱，全部类型化 | 否决：厂商 API 本身就是 `IOCTL(cmd, argv)` 且部分无文档，类型化只能覆盖已知命令 |

采纳 C 的四条依据：

1. **`Device: Sync` 与独占句柄冲突**（A 的硬伤）。
2. **可被 `as_*` 发现就等于万能控制面**：弱路径永远可达，正是 v1 的问题；v2 删 `Control` 的论证会因此失效。
3. **它回答不了"能不能"**：`as_raw_control()` 返回 `Some` 只表示"有条不透明通道"，不表示任何具体能力，违反"能力查询必须回答能不能"。
4. **真实形状与实现数**：v2 的全局 `RawControl` 实现数为 0；真实面是每设备一个（7 处）。零实现的抽象按 v2 自己的判据就不该存在。

代价与何时重开：

- **代价**：泛型代码无法"探测设备有没有原始通道再统一调用"；诊断/工装工具也不能只凭名字对任意设备发厂商命令。
- **重开条件**：若出现"对任意设备统一发厂商命令"的运维需求（诊断 shell、量产工装、现场排障），加**独立的 admin 路由**——按设备名 + op + 白名单，走 core 层（§5.15）并带审计；不要把它加回 `Device` 的能力集（权限与风险模型不同）。
- **签名细节**：op 取 `u32`（厂商 `ulong cmd`）；返回 `Result<isize, DeviceError>`——原始通道也要能报错与回传标量，否则调用方只能靠约定。

## 8. 一句话

> L2 收口后的版本：内核只保留“接设备”的那一层（发现/生命周期/阻塞/上下文分级/逃生舱）；
> 框架层与总线词汇归产品层。见 §9。


形状已经对齐 Linux，不需要再加大抽象；真正缺的是**框架层那一层**——仲裁、生命周期、probe 回滚、
寄存器访问助手、背压语义。补上 §5.15 与 §5.8 满时语义，这份规范才"能指导实现"；
砍掉零实现预留面与自我辩护，它才"能被维护"。

## 9. 范围收口（L2，2026-10-30）

> 本节是对 §3.1/§3.5 结论的**范围修正**：那些“设计不足”的补法（core 层、`RegMap`、仲裁）
> 不再进内核，而是留给产品层。本文其余部分作为决策记录保留。

判定：内核设备层的职责是**“把设备接进调度器”**，不是重新定义片内外设词汇。

**保留在内核**：`DeviceBase`/`Device`、注册表/清单（`define_capabilities!` 单一事实源）、
`StreamDevice`/`BlockDevice`/`EventDevice`/`Switchable`、`read_blocking`、C0/C1/C2（R8）、
`IoCtl` 逃生舱、`EventChannel`。

**移出内核（产品层 / 未接通）**：

- `BusDevice`（及 `as_bus`/`find_bus`/`Capability`）：SPI/I2C 词汇由 `embedded-hal` 提供，
  内核不再重复定义；
- `RegMap`、`BusArbiter`、`claim_owner`/`OwnerGuard`：树内**没有真实总线器件的端到端消费者**，
  按“有实现才有能力”的规矩不进内核；完整实现保留在 `wip/device-v3-phase3`；
- 执行模型骨架（`SyncOp` 等）、`Openable`/`Recoverable` 参考实现：设计保留、代码不预置。

**重开条件**：树内出现第一个真实 I2C/SPI 器件（至少一条端到端调用）时，以**产品层小工具**
的形式引入总线仲裁/寄存器助手（对齐 `embedded-hal-bus` 的形状），不进能力目录。
